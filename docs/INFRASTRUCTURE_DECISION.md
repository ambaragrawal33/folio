## 6. Database, backups, Redis and email gates

**Proposed A backup design:** bounded daily backup task inside the paid API deployment, with lease/timeout/resource limits, an authenticated manifest and external heartbeat; stream compressed client-side encrypted dumps to private R2 Standard, with encryption recovery material stored independently of host/provider secrets. Target 14 daily + 4 weekly backups **only while measured storage stays below 10GB**; set retention/usage alerts. A separate isolated restore drill verifies ledger counts, Decimal128, ownership and projections. Proposed target **RPO 24h / RTO 4h** is unapproved and unmeasured. A lost scheduler run requires alert/catch-up; the storage allowance is not a contractual budget cap. No tools/job/backup policy are implemented by this research.

**Important consistency boundary:** Atlas Free does not support `mongodump --oplog` or `mongorestore --oplogReplay`. A dump while writes occur can be inconsistent. For A, approve and verify a brief coordinated all-write drain before backup, including relevant auth/system writes, or choose a supported managed snapshot tier. Read-only portfolio access alone does not prove the entire database is write-free. Stop if acceptable consistency cannot be demonstrated. [Atlas tool restrictions](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/), [mongodump consistency](https://www.mongodb.com/docs/database-tools/mongodump/).

Flex automatically enables daily snapshots; retains the last eight, supports restore/download, and does not provide on-demand snapshots/custom snapshot frequency at this tier. That is B's primary reliability improvement, not a promise of PITR or zero data loss. [Atlas backup overview](https://www.mongodb.com/docs/atlas/backup-restore-cluster/), [Flex snapshot policy](https://www.mongodb.com/pt-br/docs/atlas/backup/cloud-backup/flex-cluster-backup/).

Do not put database dumps in Git, public Actions artifacts, frontend assets or publicly reachable buckets. Narrow database network access and least-privilege backup credentials are required. GitHub-hosted runner egress is not a static allowlist; do not open Mongo to the world for convenience. GitHub scheduled workflows are best-effort and can be delayed or disabled after inactivity in public repositories; they are not the sole production scheduler. [Schedule behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Keep Redis security state persistent and test disconnect/restart/quota cases. An old Redis backup must not silently restore weaker replay/throttle state; define conservative recovery and reauthentication before declaring restore safe. Never evict security counters merely to make room for market cache. Paid HA or migration requires separate capacity/security review.

For O04, propose Resend Free over HTTPS with a verified sending subdomain, SPF/DKIM/DMARC, safe retry/idempotency handling, quotas and real verification/reset delivery tests. DNS authentication improves legitimacy but cannot guarantee inbox delivery. No paid mailbox or self-hosted mail server is needed. **The current API has no production email adapter**; adding one is future authorized work. Read-only demo does not silently waive O04. Current provider rights/keyed smoke remain mandatory; spending on hosts cannot resolve Yahoo display entitlements or remove CoinGecko Demo requirements.

## 7. Migration, lock-in and upgrade path

Keep a normal Docker API, standard MongoDB collections/Decimal128 and Redis TCP/Lua. Cloudflare-specific code is limited to the future small HTTP proxy and deployment configuration; standard S3-compatible encrypted objects support backup portability. Move compute without rewriting the ledger. Migration still needs dataset/transaction compatibility checks, schema/rollback planning, Redis recovery policy, latency/allowlist tests and a restore drill; it is not zero effort. Moving browser origin invalidates host-bound cookies and requires reauthentication.

For same-origin `/api`, narrowly route a Pages Function to the selected API. Preserve methods/bodies/Set-Cookie, `no-store` and security headers; strip untrusted client forwarding headers, authenticate proxy ingress where appropriate, and verify direct-origin/IP-spoof/HTTPS behavior. The existing API must use the selected public `WEB_ORIGIN` and verified trusted-proxy handling. [Function routing](https://developers.cloudflare.com/pages/functions/routing/) is supported; its deployed cookie/security behavior is **not yet verified**. Static `_redirects` alone is not the proposed external API proxy. No financial calculations or auth password work move to the edge.

Upgrade by measured bottleneck: API memory/CPU/concurrency first; Atlas Flex when backup consistency/capacity warrants it; Redis paid capacity when measured command/memory limits require it. Then dedicated Mongo with suitable recovery, stronger Redis availability, more than one API instance and load balancing for actual service commitments. Do not jump to Kubernetes, paid team workspaces, dedicated email IPs or multi-cloud duplication at this stage. No trial-credit architecture, unavailable VPS capacity or untested serverless runtime is treated as an assured free production solution.
